# Streamhub 压测报告

所有数字都来自 `loadtest/results/` 里的原始文件（每次一个 JSON + 一行摘要），没有估算值。关键场景都跑了两遍。
测试时间：2026-11-20 16:00–17:00（北京时间，UTC+8）。

## 1. 测试环境（重要：所有东西挤在一台机器上）

| 项 | 值 |
|---|---|
| 机器 | 1 台 KVM 虚拟机，8 vCPU（Intel Xeon），16 GB 内存，Linux 6.12 |
| JDK / 应用 | OpenJDK 21.0.13，`-Xms768m -Xmx768m`，G1；Netty IO 线程 = 2×核数 = 16 |
| MySQL | 8.4.5，buffer pool 256M，`innodb_flush_log_at_trx_commit=1`、`sync_binlog=1`（都是最安全的默认值，每次提交都刷盘） |
| Redis | 8.0.2 |
| RocketMQ | 5.3.3，单 NameServer + 单 Broker，ASYNC_FLUSH；topic `danmaku` 8 个队列；`maxTransferCountOnMessageInMemory=1024`（默认 32 会把一次拉取卡在 32 条） |
| 压测客户端 | 自己写的 Go 程序 `loadtest/client`（gorilla/websocket），**和服务端在同一台机器上** |
| 应用配置 | 默认值：合并窗口 100ms / 50 条，每用户 5 条/秒（突发 10），在途上限 2000 |

**怎么读这些数字**：客户端、应用、MySQL、RocketMQ 抢同一台机器的 8 个核。每秒 4000 条以上、或 3 万连接以上时，整机 CPU 空闲接近 0%，客户端本身吃掉 3～7 个核（`results/top_r5000.txt`、`results/top_conn40k.txt`）。所以高负载段的延迟是"这台机器的上限"，不能全算在服务端头上。真要测服务端极限，需要把客户端放到别的机器上。

### 关于作废的数据
第一版压测客户端有个 bug：发送者的起始时间只在发送间隔的一小段里错开（按 `i/1000` 而不是 `i/发送者数`），低速率时所有人几乎同时发，流量变成一阵一阵的。那批数据移到了 `results/invalid_bursty_client/`，**不使用**。修好之后全部重跑，本报告只用重跑的结果。

## 2. 测试方法

- 一个房间（视频），`receivers` 个纯观众 + `rate/4` 个发送者（每人 4 条/秒，低于 5 条/秒的限流）。发送者也在房间里，也会收到推送。
- 每个节点挑 50～100 个观众解析每条消息，用消息里的发送时间算**推送延迟**（发出 → 观众收到）。**ack 延迟** = 发出 → 收到服务端确认（确认在 MQ 写成功之后才回）。
- 投递率 = 抽样观众收到的条数 / 服务端 ack 的条数。
- 每轮测 20 秒，停止发送后再等 3 秒收尾。服务端 CPU 用 `/proc/<pid>/stat` 算平均占用核数。

## 3. 结果

### 3.1 单房间最大持续吞吐（1000 观众，合并开启）

| 速率(条/秒) | 轮次 | 投递率 | 推送 P50 / P99 | ack P50 / P99 | 服务端 CPU(核) | BUSY / 限流 / 断连 |
|---|---|---|---|---|---|---|
| 1000 | 1 / 2 | 100% / 100% | 30 / 58ms，31 / 60ms | 0.35 / 10ms，0.35 / 12ms | 0.73 / 0.75 | 0 / 0 / 0 |
| 2000 | 1 / 2 | 100% / 100% | 19 / 41ms，19 / 37ms | 0.5 / 16ms，0.4 / 13ms | 1.26 / 1.25 | 0 / 0 / 0 |
| **3000** | 1 / 2 | 100% / 100% | **15 / 41ms，15 / 41ms** | 1.8 / 26ms，1.9 / 25ms | 1.53 / 1.50 | 0 / 0 / 0 |
| 4000 | 1 / 2 | 100% / 100% | 29 / 440ms，49 / 1174ms | 21 / 414ms，39 / 944ms | 1.89 / 1.96 | 0 / 0 / 0 |
| 5000 | 1 / 2 | 68.5% / 69.4% | 1.7s / 6.9s，1.8s / 7.0s | 1.1s / 4.8s，1.0s / 4.8s | 2.17 / 2.08 | 0 / 5 / 0，0 / 0 / 0 |

结论：
- **这台机器上，干净的持续上限是 3000 条/秒**：两轮都是 100% 投递、P99 约 41ms、零错误。
- 4000 条/秒时全部送达，但 P99 抖到 0.4～1.2 秒；5000 条/秒时整机打满，慢客户端被跳过（`slowSkipped` 58～64 万次），投递率降到约 69%。但**连接一条没断，服务端也没崩**，并且每一条 ack 过的弹幕都落了库（`persistInserted = acked`）。
- 5000 条/秒那轮出现 5 次 RATE_LIMITED：客户端积压后补发，同一用户 1 秒内超过了 5 条，属于限流正常工作。
- 另外做过 6000 / 8000 条/秒的探测（旧客户端，仅定性参考），服务端开始返回 BUSY 而不是断连，说明背压是生效的。

### 3.2 合并推送：开 vs 关（1000 观众，各两轮）

| 速率 | 模式 | 写次数(channelWrites) | 服务端 CPU(核) | 推送 P50 | 推送 P99 | 投递率 |
|---|---|---|---|---|---|---|
| 500/s | 开 | 228,375 / 228,375 | 0.41 / 0.39 | 55 / 55ms | 106 / 106ms | 100% |
| 500/s | 关 | 11,390,625 / 11,388,375 | 2.85 / 2.52 | 4 / 4ms | 455 / 22ms | 100% |
| 1000/s | 开 | 506,250 ×2 | 0.73 / 0.75 | 30 / 31ms | 58 / 60ms | 100% |
| 1000/s | 关 | 2499 万 / 2503 万 | 4.6 / 4.7 | 1.15s / 1.28s | 6.2s / 6.6s | 100% |
| 2000/s | 开 | 1,215,000 ×2 | 1.26 / 1.25 | 19 / 19ms | 41 / 37ms | 100% |
| 2000/s | 关 | 3729 万 / 4115 万 | 5.17 / 5.74 | 8.5s / 7.3s | 17.6s / 15.9s | 52.7% / 56.7% |

结论：
- 500 条/秒时，合并让写次数**少了 98%**（50 条一帧），CPU **省了约 85%**。
- 代价是延迟：不合并时 P50 只有 4ms，合并后约 55ms（要等窗口）。这是有意的取舍：弹幕晚 0.1 秒没人察觉，但 CPU 省下来的空间决定了能撑多大的房间。
- 不合并到 1000 条/秒，P99 已经到 6 秒；到 2000 条/秒，CPU 吃到 5～6 核，投递率掉到一半出头，还出现少量断连（1 / 10 次）和 ack 来不及在收尾窗口内回来（`acked < sent`）的情况。合并开启时同样速率一切正常。
- "关 500/s" 第一轮 P99 455ms、第二轮 22ms：第一轮紧跟着节点重启，JIT 还没预热，所以两轮差别大。

### 3.3 单房间连接数（200 条/秒，50 个发送者）

| 连接数 | 轮次 | 建连成功 | 投递率 | 推送 P50 / P99 | ack P99 | 服务端 CPU(核) |
|---|---|---|---|---|---|---|
| 1k | 1 / 2 | 全部 | 100% | 58 / 113ms，56 / 107ms | 8 / 4ms | 0.77 / 0.27 |
| 5k | 1 / 2 | 全部 | 100% | 66 / 131ms，63 / 128ms | 24 / 20ms | 0.66 / 0.51 |
| 10k | 1 / 2 | 全部 | 100% | 71 / 147ms，76 / 157ms | 39 / 47ms | 0.86 / 0.87 |
| 20k | 1 / 2 | 全部 | 100% | 65 / 137ms，74 / 161ms | 43 / 75ms | 1.39 / 1.51 |
| 30k | 1 / 2 | 全部 | 100% | 91 / 208ms，341ms / 3.2s | 107ms / 3.2s | 1.89 / 2.09 |
| 40k | 1 / 2 / 3 | 全部 | 100% | 3.7 / 10.6s，1.8 / 6.3s，1.5 / 5.9s | 5～10s | 1.9～2.5 |

结论：
- **2 万连接以内很稳**：100% 投递，P99 在 160ms 以内（其中约 100ms 是合并窗口本身）。
- 3 万连接时一轮正常（P99 208ms）、一轮变慢（P99 3.2s）；4 万连接三轮都是秒级延迟，但**投递率仍是 100%，没有断连，也没有慢客户端被跳过**。
- 4 万连接时机器已经打满：测量期间整机空闲 0%，**压测客户端吃 3.2～4.9 个核，服务端只有 1.7～2.5 个核**（`results/top_conn40k.txt`）。客户端每秒要读约 30 万帧。所以这一档的延迟主要受这台机器和客户端限制，不能直接算成服务端的上限。
- 和旧项目 EchoFrame 比（同一台机器，4 万连接时 P99 是 1.8～7.9 秒）：新实现到 4 万连接时在这台机器上也是秒级延迟，而且这一档主要卡在机器和客户端上，**所以在 4 万这一档，这台机器测不出两者谁更好**，不能拿来说新实现更快。能确定的是：2 万连接以内，新实现的 P99 稳定在 161ms 以内。

### 3.4 一致性：MQ 重复投递 3 次（`loadtest/consistency_dup.sh`）

直接往 MQ 塞 2 万条不同 id 的弹幕，每条投 3 遍（共 6 万条消息），等落库消费完后核对：

| 轮次 | 消费的消息 | 实际插入 | 表行数 | 不同 id 数 | 计数表 count | 落库失败 |
|---|---|---|---|---|---|---|
| 1 | 60,000 | 20,000 | 20,000 | 20,000 | 20,000 | 0 |
| 2 | 60,000 | 20,000 | 20,000 | 20,000 | 20,000 | 0 |

重复的 4 万条被 `INSERT IGNORE` 挡掉，计数只加了真正插进去的行，**没有多算**。

### 3.5 一致性：压测中 kill -9（`loadtest/consistency_kill.sh`）

1000 条/秒持续发送，第 12 秒 `kill -9` 节点，2 秒后重启，等落库追平后逐条核对：

| 轮次 | 客户端收到 ack 的条数 | 库里行数 | 不同 id | 计数 | ack 了但库里没有 | 库里有但没 ack | 重启后重投的消息 / 实际插入 |
|---|---|---|---|---|---|---|---|
| 1 | 9,898 | 9,898 | 9,898 | 9,898 | **0** | 0 | 10 / 1 |
| 2 | 9,734 | 9,734 | 9,734 | 9,734 | **0** | 0 | 10 / 1 |

- **ack 过的弹幕一条不丢**：因为 ack 只在 MQ 确认之后才回，消息已经在 Broker 上了，节点死了也不影响。
- 重启后 RocketMQ 重投了 10 条（处理过但进度还没提交的），其中 9 条是重复的被跳过，1 条是 kill 时还没来得及写库的，补上了。库里没有重复、计数准确。

### 3.6 落库吞吐 vs 写入速度（`loadtest/drain.sh`）

先停节点，往 MQ 里堆 50 万条积压，再启动节点，看多快写完：

| 轮次 | 积压 | 从第一行写入到全部写完 | 行/秒 | 平均每批 | 每批 DB 耗时 |
|---|---|---|---|---|---|
| 1 | 500,000 | 4.28s | **116,806** | 199.7 条 | 6.3ms |
| 2 | 500,000 | 4.69s | **106,700** | 199.7 条 | 6.5ms |

（第一次用 10 万条试的时候只用了 1～2 秒，太短，计时误差大，所以加到 50 万条。）

- 落库能力约 **10 万行/秒**，是写入上限（3000 条/秒）的 30 多倍，正常情况下落库永远不会成为瓶颈。前面所有压测里，窗口结束时 `persistInserted` 都等于 `acked`，没有积压。
- 对比 EchoFrame 的约 630 行/秒：差别来自"每批 200 条、一条多行 INSERT、一个事务、拉取间隔 0、4 个线程"，以及 Broker 的单次拉取上限调到 1024。
- 注意：这里的 MySQL 是默认的"每次提交都刷盘"，批越大刷盘次数越少，这正是批量写的意义。

### 3.7 两个节点（`loadtest/two_node.sh`）

节点 a（8080/9100）和 b（8081/9101），同一个房间；2000 个观众和 250 个发送者轮流连两个节点，1000 条/秒：

| 轮次 | 投递率 a / b | 推送 P50 / P99 | ack 数 | 不同 ack id | 按 workerId 分 | 库里行数 / 不同 id / 计数 | ack 了库里没有 |
|---|---|---|---|---|---|---|---|
| 1 | 100% / 100% | 40 / 378ms | 20,250 | 20,250 | worker 0: 10,125，worker 2: 10,125 | 20,250 / 20,250 / 20,250 | 0 |
| 2 | 100% / 100% | 36 / 71ms | 20,250 | 20,250 | worker 0: 10,125，worker 2: 10,125 | 20,250 / 20,250 / 20,250 | 0 |

- **跨节点投递成立**：每个节点只收了一半的发送（各 10,125），但每个节点的广播消费者都收到了全部 20,250 条，两边观众的投递率都是 100%。
- **ID 不冲突**：两个节点从 Redis 抢到不同的 workerId（0 和 2），2 万多个 id 全部不同。
- 落库是集群消费，两个节点各写了大约一半（10,131 + 10,119），合起来不多不少。
- workerId 是 0 和 2 而不是 0 和 1：1 号还被一个之前被关掉的旧进程占着，要等 60 秒过期（见第 4 节第一条）。
- 第 1 轮 P99 378ms 是因为两个节点刚启动、JIT 还没预热；第 2 轮 71ms。

## 4. 压测中发现并修掉的问题

1. **正常关闭时 workerId 没归还**：本来用 `@PreDestroy` 归还，但那时 Redis 连接已经被 Spring 关掉了（Lettuce 连接工厂的生命周期阶段是 0，会先停），归还悄悄失败，号只能等 60 秒过期。改成 `SmartLifecycle`，阶段 5：在 Netty 和消费者停止之后、Redis 关闭之前归还，并加了单元测试。修复后 `kill -TERM` 节点，Redis 里的 key 立刻消失（已验证）。
2. **同名节点重启后会被当成同一个持有者**：之前用 nodeId 当持有者标识，同名的新进程可能续上旧进程留下的号。现在持有者标识 = nodeId + 随机后缀。
3. **压测客户端发送时间分布不均**：见 1 节"作废的数据"。

## 5. 复现

```bash
# 中间件就绪、seed.sql 导入后
./mvnw -q package -DskipTests
loadtest/run_node.sh a 8080 9100                    # 合并关闭：加 MERGE_WINDOW_MS=0
loadtest/lt.sh tput_r3000 -receivers 1000 -rate 3000 -duration 20s
loadtest/consistency_dup.sh 1
loadtest/consistency_kill.sh 1
loadtest/drain.sh 1
loadtest/run_node.sh b 8081 9101 && loadtest/two_node.sh 1
```
客户端编译：`cd loadtest/client && go build -o ltclient .`。MqInjector 需要先生成 classpath：`./mvnw dependency:build-classpath -Dmdep.outputFile=loadtest/tools/cp.txt`。
