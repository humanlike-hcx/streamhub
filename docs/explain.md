# Streamhub 大白话讲解

这份文档的目标：你读完以后，能对着代码把每一块讲清楚，面试时被追问也接得住。
先讲整体，再跟着一条弹幕走一遍，然后逐个模块讲，最后是取舍和面试题。

---

## 一、整体：三件事分开做

一条弹幕要办三件事：

1. **告诉发送者"发成功了"**（ack）
2. **推给房间里所有正在看的人**（实时推送）
3. **存进数据库**，以后打开视频还能看到（落库）

这三件事的要求完全不一样：
- ack 要**可靠**：说了成功就不能丢。
- 推送要**快**，但偶尔丢一两条没人在意。
- 落库要**不丢、不重复**，但晚几秒没关系。

所以设计的核心就是：**先把弹幕可靠地放进消息队列（RocketMQ），然后再回 ack；推送和落库各自从队列里拿，互不影响。**
数据库慢了，不影响推送；某个观众网卡了，也不影响落库。

```
发送者 ─▶ 网关(Netty) ─▶ RocketMQ ─┬─▶ 广播消费(每个节点都收) ─▶ 本节点房间 ─▶ 观众
               ▲                   │
               └── MQ 确认后回 ack   └─▶ 集群消费(全集群只处理一次) ─▶ MySQL
```

## 二、跟着一条弹幕走一遍

假设小明在看视频 1，发了一句"前方高能"。

**① 建立连接**
小明的浏览器连 `ws://服务器:9100/ws/room/1`。Netty 的 `WebSocketServerProtocolHandler` 完成握手，
`WsHandler` 从路径里解析出视频 id = 1，调用 `RoomRegistry.join` 把这个连接放进房间 1。
现在小明已经能看弹幕了（游客）。

**② 登录**
小明发的第一条消息是 `{"op":"auth","token":"..."}`。`JwtVerifier` 校验签名和过期时间，拿到 userId，回 `authOk`。
为什么 token 不放在 URL 里？URL 会被记进各种访问日志，token 就泄露了。

**③ 发弹幕**
小明发 `{"op":"send","clientSeq":7,"content":"前方高能","color":"#ffffff","playbackTime":61.2}`。
`WsHandler` 把它交给 `IngestService.submit`，依次过几道关：

| 关卡 | 不通过时 | 代码 |
|---|---|---|
| 内容 1～100 字、颜色格式、播放时间 ≥ 0 | 回 `INVALID` | `valid()` |
| 这个用户每秒不超过 5 条（可以连发 10 条） | 回 `RATE_LIMITED` | `UserRateLimiter` + `TokenBucket` |
| 整个节点"发出去还没回音"的请求不超过 2000 个 | 回 `BUSY` | `Semaphore.tryAcquire()` |
| 视频存在且开着弹幕（查缓存，没有才查库，异步） | 回 `VIDEO_CLOSED` | `CachedVideoGate` |

**任何一关不过，都只回一条错误消息，连接不断。** 客户端可以过一会儿重试。

**④ 生成 ID**
`SnowflakeIdGenerator.nextId()` 生成一个 64 位整数 id，全局唯一、大致按时间递增。后面推送、落库、去重都认这个 id。

**⑤ 发 MQ，然后回 ack**
`RocketMqPublisher.publish` **异步**把消息发给 RocketMQ：交出去就返回，不等结果，Netty 线程马上去处理别的连接。
等 Broker 回复"存好了"，回调里才给小明回 `{"op":"ack","clientSeq":7,"id":"..."}`，同时把那个"在途名额"还回去。
如果 MQ 失败，回 `BUSY`。所以小明看到 ack 的那一刻，消息一定已经在 MQ 里了。

**⑥ 推送：广播消费**
每个节点上都有一个 `BroadcastConsumer`，用的是**广播模式**，同一条消息每个节点都会收到一份。
它把弹幕转成 JSON，调用 `RoomRegistry.publish(1, json)`。
房间 1 被拆成若干个"分片"（每个 Netty 线程一个），`publish` 把这条弹幕交给每个分片自己的线程。

**⑦ 合并推送**
分片不马上推，而是先攒着：攒够 50 条，或者等满 100ms，再把这些弹幕拼成一帧 `{"op":"batch","items":[...]}`，
**只编码一次**，然后发给分片里的每个连接。
发之前看一眼 `isWritable()`：这个连接的发送缓冲区已经堆了超过 1MB 还没发出去，说明对方网很差，这一帧就跳过它。

**⑧ 落库：集群消费**
同时，`PersistConsumer`（**集群模式**，整个集群里每条消息只有一个节点处理）一次拿最多 200 条，
交给 `DanmakuWriter`：在一个事务里，每个视频一条多行 `INSERT IGNORE`，再把这个视频的计数加上"真正插进去的行数"。
成功了才告诉 MQ "处理完了"；失败就整批稍后重来。

整条路下来，小明 1ms 左右拿到 ack，房间里的人大约 15～60ms 后看到弹幕，数据库里几毫秒后就有了。

## 三、逐个模块

### gateway：网关

- **`NettyServer`**：启动 WebSocket 服务器。1 个 boss 线程负责接新连接，16 个 worker（EventLoop）线程负责读写。
  - `TCP_NODELAY`：小包不等，立即发。
  - 写缓冲水位 512KB / 1MB：超过 1MB，`isWritable()` 变成 false，用来识别慢客户端。
  - `IdleStateHandler(30s)`：30 秒没收到任何东西就发一个 ping；连续两次都没回应，就当连接已经死了，关掉。
- **`WsHandler`**：每个连接一个实例。一个连接的所有事件都在同一个线程里按顺序执行，所以它的字段不用加锁。
  路径不合法（比如 `/ws/room/abc`）就用 1008 关闭码关掉。
- **`JwtVerifier`**：HS256 签名校验。
- **`DevController`**：开发用的"发 token / 开视频"接口，只有 `DEV_ENDPOINTS=true` 时才存在，生产环境默认没有。

### ingest：发送链路

- **`IngestService`**：上面第③～⑤步。重点有两个：
  1. **全程不阻塞 Netty 线程**：查视频状态是异步的，发 MQ 是异步的。Netty 线程如果被卡住，它负责的几千个连接都会跟着卡。
  2. **`Permit` 类保证在途名额"恰好还一次"**：异步代码有很多结束路径（视频关了、ID 生成失败、MQ 成功、MQ 失败），
     每条路径都要还名额。万一某个回调被调了两次，信号量就会凭空多出名额，背压就失效了。`AtomicBoolean` 防止重复归还。
- **`TokenBucket` / `UserRateLimiter`**：令牌桶。每个用户一个桶，每秒补 5 个令牌，最多存 10 个，发一条消耗一个。
  桶放在 Caffeine 缓存里，用户一段时间不活跃就自动清掉，不会无限占内存。
- **`CachedVideoGate`**：视频是否开着弹幕。Caffeine `AsyncLoadingCache` 缓存 30 秒，没命中时在一个 4 线程的小线程池里查 MySQL。
  同一个视频同时来 1000 个请求，也只会查一次库。
- **`RocketMqPublisher`**：原生 `DefaultMQProducer`，异步发送，失败自动重试 2 次，超时 3 秒。
- **`BroadcastConsumer`**：广播消费组 `streamhub-push`，从"最新"位置开始消费，超过 10 秒的旧消息直接扔掉
  （节点刚重启时，推 10 秒前的弹幕没有意义，反而会刷屏）。

### room：房间

- **`RoomRegistry`**：视频 id → `Room` 的表（`ConcurrentHashMap`）。还有一个每秒执行的任务，人数变化时推送在线人数。
- **`Room`**：一个视频的房间，按 EventLoop 拆成多个 `RoomShard`。
- **`RoomShard`**：本项目最核心的类。
  - **为什么按 EventLoop 分片？** Netty 里每个连接一辈子只属于一个线程。
    把同一个线程上的连接放进同一个分片，分片的所有操作都在这个线程里做，**就完全不需要锁**；16 个分片在 16 个线程上并行推送。
    反面例子：一个线程拿着房间锁，给 4 万个连接挨个写，这一个线程就是瓶颈。
  - **合并（`append` / `flush`）**：攒 50 条或 100ms，或者再加一条会超过 16KB，就推一次。`windowMs=0` 表示关闭合并（压测对比用）。
  - **只编码一次（`retainedDuplicate`）**：一帧内容转成字节只做一次，每个连接拿到的是共享这块内存的"视图"（只增加引用计数，不复制）。
  - **慢客户端跳过**：`!ch.isWritable()` 就跳过，计入 `slowSkipped`。

### persist：落库

- **`PersistConsumer`**：集群消费组 `streamhub-persist`，4 个线程，一批最多 200 条，拉取间隔 0。
  解析不了的消息（"毒消息"）记日志跳过，否则它会一直重试，把整个队列卡住。
- **`DanmakuWriter`**：
  1. 按视频 id 排序分组（`TreeMap`）。**所有事务都按同样的顺序加锁，就不会死锁**（A 锁 1 等 2、B 锁 2 等 1 的情况不会出现）。
  2. 每个视频一条多行 `INSERT IGNORE`：主键（雪花 id）重复的行被跳过。返回的"影响行数"就是真正插入的条数。
  3. `INSERT ... ON DUPLICATE KEY UPDATE count = count + n`：计数只加真正插进去的条数。重复消息不会让计数变多。
  4. 以上全部放在一个事务里：要么全成功，要么全回滚。
- **`HistoryController`**：按播放时间段查历史弹幕（用 `(video_id, playback_time)` 索引）、查总数。

### common：公共

- **`SnowflakeIdGenerator`**：64 位 = 1 位符号 + 41 位毫秒时间戳（从 2026-01-01 起，够用 69 年）+ 10 位 workerId（最多 1024 个节点）+ 12 位序号（每毫秒 4096 个）。
  时钟往回拨 5ms 以内就等一等；超过就抛异常，上层回 BUSY。绝不能发出重复 id。
- **`WorkerIdLease`**：workerId 从哪来？启动时在 Redis 里从 0 开始尝试 `SET streamhub:worker:n 我的名字 NX PX 60000`，第一个成功的就是我的号。
  - 每 20 秒用 Lua 脚本"确认还是我的，再续 60 秒"。
  - **安全边界**：本地只把租约当作 50 秒（60 − 10）有效。如果一直连不上 Redis，本节点会在 Redis 里的 key 过期**之前**停止发号，
    所以别的节点接手这个号的时候，我们已经不用它了，不会出现两个节点同号。
  - 正常关闭时主动还号。环境变量 `STREAMHUB_WORKER_ID` 可以直接指定，不走 Redis。
- **`Metrics` / `MetricsController`**：用 `LongAdder` 计数（高并发下比 `AtomicLong` 快），`GET /metrics` 查看。
- **`Protocol`**：所有 JSON 消息的格式。id 以字符串发出去，因为 JavaScript 的数字只有 53 位精度，64 位 id 会被截断。

### 启动和关闭顺序（SmartLifecycle）

| 阶段 | 组件 | 启动 | 关闭 |
|---|---|---|---|
| 0 | MQ 生产者、Redis 连接 | 最先 | 最后 |
| 5 | workerId 租约 | 抢号 | 还号 |
| 10 | 两个 MQ 消费者 | | |
| 20 | Netty 网关 | 最后（一切就绪才接客） | 最先（先停止接新请求） |

压测时发现过一个真问题：最早还号写在 `@PreDestroy` 里，但那时 Redis 连接已经关了，还号悄悄失败。改成阶段 5 以后修好了。

## 四、取舍（为什么这样选，代价是什么）

| 决策 | 选择 | 好处 | 代价 |
|---|---|---|---|
| 跨节点推送 | MQ 广播消费（1A） | 不用另外引入 Redis Pub/Sub，复用已有的 MQ；节点之间不用知道彼此 | 每个节点都收全量消息，节点很多时浪费；推送多一跳 MQ 的延迟 |
| workerId | Redis 租约（2B） | 扩容不用手动配号 | 依赖 Redis；要处理续期失败、时钟问题 |
| 落库 | 一个事务里批量 INSERT IGNORE + 计数（3A） | 幂等、快（实测约 10 万行/秒） | 批里一条坏了整批重试；计数要和明细同库 |
| ack 时机 | MQ 确认后再 ack（4A） | ack 了就不会丢 | 多等一次 MQ 往返（实测 P50 约 0.4～2ms） |
| 合并 | 固定 100ms / 50 条（5A） | 写次数少 98%，CPU 少约 85% | 每条弹幕多等最多 100ms |
| 慢客户端 | 跳过帧 | 一个人网差不拖垮整个房间，内存不爆 | 这个人会少看到一些弹幕 |
| 过载 | 回 BUSY，不断连 | 客户端可以重试，不会集体重连形成雪崩 | 客户端要处理 BUSY |
| 限流/在线人数 | 单节点内存 | 简单、快，不用访问 Redis | 多节点时不精确 |

## 五、面试题（结合这个项目答）

**1. 讲讲一条弹幕从发出到别人看到的全过程。**
按第二节的 ①～⑧ 讲。关键词：首条消息 JWT 认证 → 校验/限流/在途上限 → 雪花 id → 异步发 MQ → MQ 确认后回 ack → 广播消费到每个节点 → 按 EventLoop 分片 → 100ms/50 条合并 → isWritable 跳过慢客户端；另一条线：集群消费 → 批量幂等写库。

**2. 为什么要引入 MQ？直接写库再推送不行吗？**
直接写库：数据库一慢，发弹幕就慢，推送也跟着慢。用 MQ 解耦以后，ack 只依赖 MQ 写入（毫秒级），推送和落库各自消费、互不影响；数据库挂了，消息也还在 MQ 里，恢复后自动补写。压测里落库有 10 万行/秒的余量。

**3. 多个节点，A 节点上的人发弹幕，B 节点上的人怎么看到？**
RocketMQ 的广播消费：同一个消费组用 BROADCASTING 模式，每个节点都收到每一条。两节点压测里，每个节点只接收了一半的发送请求，但广播消费者都收到了全部 20,250 条，两边观众的投递率都是 100%。

**4. 同一个 topic，为什么推送用广播、落库用集群？**
推送：每个节点都有自己的观众，所以每个节点都要拿到每一条。落库：全集群只能写一次，所以要让多个节点"分摊"。RocketMQ 里两个不同的消费组订阅同一个 topic，各自有各自的消费进度，互不影响。

**5. 怎么保证"ack 了就不丢"？**
ack 在 MQ 的发送回调里才回，这时消息已经在 Broker 上了。压测中 kill -9 节点两次，ack 过的近 2 万条弹幕在库里一条不少。
追问"Broker 挂了呢"：这里 Broker 是异步刷盘、单机部署，Broker 机器断电可能丢最近一小段数据。生产环境要用同步刷盘或者主从同步复制，代价是发送延迟变高。

**6. MQ 会重复投递，怎么保证不重复入库、计数不多算？**
id 在进 MQ 之前就生成好了，重投的消息 id 不变。`INSERT IGNORE` 遇到主键冲突就跳过；计数加的是"真正插入的行数"，而不是"收到的消息数"。压测里每条投 3 次，6 万条消息最后只有 2 万行，计数也是 2 万。

**7. 为什么不用 Redis 的 SETNX 做消息去重？**
那样要多一次 Redis 访问，而且"Redis 记了但数据库没写成"时会出现不一致。主键唯一约束是数据库自己保证的，和写入在同一个事务里，最可靠。

**8. 雪花算法的结构？时钟回拨怎么办？**
41 位时间戳 + 10 位 workerId + 12 位序号。回拨 5ms 以内就等一等；超过就拒绝发号、回 BUSY。宁可短暂不可用，也不能发重复 id。

**9. workerId 怎么分配？两个节点会不会拿到同一个号？**
Redis `SET NX` 抢号，60 秒租约，20 秒续一次。本地只把租约当 50 秒有效，续不上就在 Redis 过期之前停止发号。正常关闭时主动还号。两节点压测：workerId 分别是 0 和 2，20,250 个 id 全部不同。

**10. 为什么房间要按 EventLoop 分片？**
Netty 的连接一辈子只属于一个线程。分片 = 同一个线程上的连接，分片的操作只在这个线程上做 → 不需要锁；多个分片在多个线程上并行。一个线程拿着锁给全房间写就是单点瓶颈。

**11. 合并推送的收益和代价？窗口怎么定？**
500 条/秒时，写次数从 1139 万次降到 23 万次，CPU 从 2.5～2.9 核降到 0.4 核；代价是 P50 从 4ms 变成 55ms。不合并时到 1000 条/秒，P99 已经 6 秒。100ms 人眼基本感觉不到，50 条和 16KB 的上限保证一帧不会太大。

**12. 慢客户端怎么处理？为什么不等它？**
`isWritable()` 为 false（发送缓冲区超过 1MB）就跳过这一帧。如果等它或者无限往缓冲区里塞，内存会涨到 OOM，或者拖慢同一个线程上的其他连接。弹幕少看几条不影响体验。

**13. 背压（过载保护）怎么做的？**
三层：每个用户令牌桶（RATE_LIMITED）、每个节点在途上限 2000（BUSY）、每个连接写缓冲水位（跳过慢客户端）。都是"拒绝/跳过"而不是"排队"，所以过载时延迟不会无限增长。压测中 6000～8000 条/秒时服务端回 BUSY，没有断连。

**14. 为什么过载时回 BUSY 而不是断开连接？**
断开以后客户端会重连，几万人同时重连，又要重新握手、重新认证，负载反而更高（重连风暴）。回 BUSY 成本最低，客户端稍后重发就行。

**15. 为什么 Netty 线程里不能做阻塞操作？你是怎么避免的？**
一个 EventLoop 线程负责几千个连接，它被卡 100ms，这几千个连接都卡 100ms。查视频状态用异步缓存 + 独立线程池；发 MQ 用异步 send；数据库只在 MQ 消费线程里访问。

**16. 令牌桶和固定窗口限流的区别？**
固定窗口在窗口交界处可能瞬间放过 2 倍流量；令牌桶按时间匀速补充，同时允许一定的突发（这里最多连发 10 条）。每个用户一个桶，存在 Caffeine 里，过期自动清理。

**17. 落库为什么快？**
一批 200 条、每个视频一条多行 INSERT、一个事务只刷一次盘；4 个消费线程；拉取间隔 0；Broker 单次拉取上限从默认 32 调到 1024。实测 50 万积压 4～5 秒写完，约 10 万行/秒，每批数据库耗时 6ms 左右。

**18. 批量写会不会死锁？**
多个线程的批里可能有相同的视频，都要更新计数行。按视频 id 排序后再写，所有事务按同样的顺序加锁，就不会互相等待。计数用 `INSERT ... ON DUPLICATE KEY UPDATE` 一条语句完成，不需要先 `SELECT ... FOR UPDATE`。

**19. 节点 kill -9 以后会发生什么？**
这个节点上的连接全断，客户端需要自己重连（可以连到别的节点）。已经 ack 的消息在 MQ 里，落库由其他节点或者重启后的自己接着做；处理了但没提交进度的那一小段会被重投，靠幂等去重。实测重投了 10 条，9 条重复被跳过，1 条补写。它占着的 workerId 60 秒后过期。

**20. 这个系统的瓶颈在哪？怎么继续扩展？**
在这台 8 核机器上，单房间约 3000 条/秒、2 万连接以内很稳；再往上整机 CPU 被压测客户端和服务端分光了。扩展方式：加节点分摊连接（广播模式下每个节点都收全量，节点很多时可以改成按房间路由，只推给有这个房间观众的节点）；超热门房间可以在客户端抽样展示；落库目前有 30 倍余量。

**21. 测试怎么做到不依赖中间件？**
依赖都抽成接口：`LeaseStore`（Redis）、`DanmakuPublisher`（MQ）、`VideoGate`（数据库）。测试里换成内存实现；Netty 用 `EmbeddedChannel`，可以手动拨时间（`advanceTimeBy`）来测合并窗口、手动设置不可写来测慢客户端。29 个测试几秒跑完。

**22. 压测时你发现过什么问题？**
（1）压测客户端的 bug 让流量一阵一阵的，测出来的合并效果偏好看，我发现以后作废重测了；（2）正常关闭时 workerId 没还掉，原因是 Spring 关 Redis 连接比 `@PreDestroy` 早，改用 SmartLifecycle 控制顺序；（3）同名节点重启会被认成同一个持有者，加了随机后缀。能讲清楚"怎么发现的"比数字本身更有说服力。
